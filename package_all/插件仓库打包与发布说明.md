# DataAggregation 插件仓库打包与发布说明

本文说明如何使用 `build_plugin_repository.sh` 将 DataAggregation 插件目录生成对象存储仓库格式的本地制品。

脚本只负责本地打包和生成 `current.json`，不会连接 OSS，也不会上传文件。上传时必须先上传不可变的 release 制品，最后再原子更新对应的 `current.json`。

## 1. 目录约定

推荐在 DataAggregation 根目录执行命令：

```bash
cd /path/to/DataAggregation
```

完整插件目录应类似：

```text
package_all/aggregation/
├── conf/
├── lib/
└── plugin/
    ├── reader/
    ├── report/
    ├── source/
    ├── transformer/
    └── writer/
```

每个待发布插件目录必须满足：

```text
plugin/{type}/{name}/
├── plugin.json              # transformer 使用 transformer.json
├── *.jar
└── libs/                    # 可选，插件依赖
```

配置文件中的 `name` 必须与目录名一致，且目录中至少包含一个 JAR。

`package_all/aggregation_lazy` 是 Worker 的运行时目录，包含 `cache`、`.state`、`.staging` 等运行状态，不应作为常规发布源。发布时应使用完整的 `package_all/aggregation`，或者使用另外准备好的、包含插件 JAR 和配置文件的干净插件目录。

## 2. 环境依赖

脚本要求 Bash、`jq`、`zip` 和 `sha256sum` 或 `shasum`：

```bash
command -v bash
command -v jq
command -v zip
command -v sha256sum || command -v shasum
```

Ubuntu/Debian：

```bash
sudo apt-get update
sudo apt-get install -y bash jq zip coreutils
```

Windows 建议在 WSL 或 Git Bash 中执行。WSL 中访问 Windows 工作区的路径示例：

```bash
cd /mnt/c/dev/ideaProject/cloud-parent-springboot3/DataAggregation
```

如果直接执行脚本失败，可以显式使用 Bash：

```bash
bash package_all/build_plugin_repository.sh --help
```

## 3. 查看帮助

```bash
bash package_all/build_plugin_repository.sh --help
```

当前支持的参数：

| 参数 | 说明 | 默认值 |
| --- | --- | --- |
| `--aggregation-home PATH` | 插件输入根目录 | `package_all/aggregation` |
| `--output-root PATH` | 本地仓库输出根目录 | `package_all/plugin-repository` |
| `--type TYPE` | 插件类型：`source`、`reader`、`writer`、`transformer`、`report`、`file-transfer` | 空 |
| `--name NAME` | 插件目录名，必须与 `--type` 一起使用 | 空 |
| `--all` | 构建所有插件 | 否 |
| `--channel CHANNEL` | 发布通道 | `production` |
| `--release RELEASE` | 不可变版本号 | 当前 UTC 时间 |
| `--runtime-version VERSION` | Worker 运行时兼容版本 | `1.0_jdk17-SNAPSHOT` |
| `--max-artifact-bytes BYTES` | 单个 ZIP 最大字节数 | `536870912` |

`--all` 不能和 `--type`、`--name` 同时使用。只传 `--type` 或只传 `--name` 也会失败。

## 4. 构建前准备完整 aggregation

如果插件制品尚未生成，先构建 DataAggregation：

```bash
mvn clean install -DskipTests
bash package_all/packe_move.sh
```

确认插件已存在：

```bash
find package_all/aggregation/plugin -mindepth 2 -maxdepth 2 -type d | sort
```

确认 `source/mysql8` 的必需文件：

```bash
find package_all/aggregation/plugin/source/mysql8 -maxdepth 2 -type f | sort
```

## 5. 构建全部插件

下面命令会生成 `production` 通道下的全部插件，使用一个全新的不可变 release：

```bash
bash package_all/build_plugin_repository.sh \
  --aggregation-home package_all/aggregation \
  --output-root /tmp/release/aggregation-plugins \
  --all \
  --channel production \
  --release codex-20260804-v1 \
  --runtime-version 1.0_jdk17-SNAPSHOT
```

推荐每次发布使用唯一的 release，例如：

```text
codex-20260804-v1
20260804-hotfix-01
release-2026-08-04-source-mysql8-v2
```

同一个通道、插件和 release 目录已经存在且包含 `plugin.zip` 时，脚本会打印 `SKIP` 并继续处理其他插件；
它不会重新打包该插件，也不会改写该插件的 `current.json`。因此可以使用同一 release 对部分发布的插件集合执行
`--all`，补齐缺少的插件制品。已存在但缺少 `plugin.zip` 的不完整 release 目录仍会导致构建失败，避免掩盖损坏制品。

## 6. 只构建一个插件

例如只构建 `source/mysql8`：

```bash
bash package_all/build_plugin_repository.sh \
  --aggregation-home package_all/aggregation \
  --output-root /tmp/release/aggregation-plugins \
  --type source \
  --name mysql8 \
  --channel production \
  --release codex-20260804-source-mysql8-v1 \
  --runtime-version 1.0_jdk17-SNAPSHOT
```

构建 MySQL reader、writer 和 transformer 的示例：

```bash
bash package_all/build_plugin_repository.sh \
  --aggregation-home package_all/aggregation \
  --output-root /tmp/release/aggregation-plugins \
  --type reader \
  --name mysql8reader \
  --channel production \
  --release codex-20260804-reader-v1

bash package_all/build_plugin_repository.sh \
  --aggregation-home package_all/aggregation \
  --output-root /tmp/release/aggregation-plugins \
  --type writer \
  --name mysql8writer \
  --channel production \
  --release codex-20260804-writer-v1

bash package_all/build_plugin_repository.sh \
  --aggregation-home package_all/aggregation \
  --output-root /tmp/release/aggregation-plugins \
  --type transformer \
  --name trim_spaces_str \
  --channel production \
  --release codex-20260804-transformer-v1
```

构建文件传输插件：

```bash
bash package_all/build_plugin_repository.sh \
  --aggregation-home package_all/aggregation \
  --output-root /tmp/release/aggregation-plugins \
  --type file-transfer \
  --name filetransfer \
  --channel production \
  --release codex-20260804-file-transfer-v1 \
  --runtime-version 1.0_jdk17-SNAPSHOT
```

`--all` 同样会自动发现 `aggregation/plugin/file-transfer/filetransfer`，生成
`production/file-transfer/filetransfer` 下的不可变 release 和 `current.json`。

## 7. 生成结果

以 `source/mysql8`、`production`、`codex-20260804-v1` 为例，输出结构如下：

```text
/tmp/release/aggregation-plugins/
└── production/
    └── source/
        └── mysql8/
            ├── current.json
            └── releases/
                └── codex-20260804-v1/
                    └── plugin.zip
```

`plugin.zip` 是插件目录本身的压缩包，解压后应直接看到 `plugin.json`、JAR 和 `libs`，不会额外包一层 `mysql8/` 目录。

脚本会先在临时目录中生成 ZIP，校验大小和 SHA-256 后，再移动到 release 目录，并最后生成 `current.json`。同一插件的多个 release 可以并存。
如果目标 release 已经完整存在，脚本只输出跳过提示，不校验或更新现有 ZIP 和 pointer；发布前仍需按已有
`current.json` 核对既有制品的 SHA-256 和大小。

## 8. current.json 字段

示例：

```json
{
  "schemaVersion": 1,
  "type": "source",
  "name": "mysql8",
  "release": "codex-20260804-v1",
  "artifact": "releases/codex-20260804-v1/plugin.zip",
  "sha256": "<64 位 SHA-256>",
  "size": 123456,
  "runtimeVersion": "1.0_jdk17-SNAPSHOT",
  "updatedAt": "2026-08-04T00:00:00.000Z"
}
```

字段含义：

- `schemaVersion`：pointer 格式版本，目前为 `1`。
- `type`、`name`：插件坐标，必须与目录一致。
- `release`：不可变 release 名称。
- `artifact`：相对于插件坐标目录的 ZIP 路径。
- `sha256`：ZIP 文件 SHA-256 小写十六进制摘要。
- `size`：ZIP 字节数。
- `runtimeVersion`：兼容的 Worker/DataAggregation 运行时版本。
- `updatedAt`：UTC ISO-8601 更新时间。

## 9. 本地校验

构建完成后检查 pointer：

```bash
jq . /tmp/release/aggregation-plugins/production/source/mysql8/current.json
```

检查 ZIP 大小和摘要：

```bash
artifact=/tmp/release/aggregation-plugins/production/source/mysql8/releases/codex-20260804-v1/plugin.zip
sha256sum "$artifact"
wc -c < "$artifact"
unzip -l "$artifact" | sed -n '1,40p'
```

摘要必须与 `current.json.sha256` 一致，文件大小必须与 `current.json.size` 一致。

批量检查所有 pointer：

```bash
find /tmp/release/aggregation-plugins/production \
  -path '*/current.json' -print0 |
while IFS= read -r -d '' pointer; do
  jq -e '.schemaVersion == 1 and (.type | type) == "string" and (.name | type) == "string" and (.release | type) == "string" and (.artifact | type) == "string" and (.sha256 | test("^[0-9a-fA-F]{64}$")) and (.size > 0) and (.runtimeVersion | type) == "string" and (.updatedAt | type) == "string"' "$pointer" >/dev/null
  echo "validated $pointer"
done
```

## 10. 发布到 OSS 的顺序

脚本生成的是本地目录，远程发布必须遵循以下顺序：

1. 备份远程原有的 `current.json`。
2. 上传不可变对象：
   `production/{type}/{name}/releases/{release}/plugin.zip`
3. 对远程 ZIP 做 HEAD/stat，核对大小和 SHA-256。
4. 最后上传或原子覆盖：
   `production/{type}/{name}/current.json`
5. 再次读取远程 `current.json`，确认 release、artifact、SHA、大小和 runtimeVersion 全部匹配。

不要先覆盖 `current.json`，也不要覆盖已经存在的 release。更新只新增 release，然后切换 pointer。

OSS 上传不由本脚本完成。生产环境应使用项目提供的 Java `PluginRepositoryObjectStorageTool`，让它复用 Worker 从 Nacos 读取的 Aliyun OSS 配置，并启用 Nacos provenance 校验；操作说明见：

```text
data-aggregation-studio/docs/运维/部署/studio-complete-deployment-guide.md
```

不要把 OSS endpoint、AccessKey、SecretKey 写入本文件、命令历史或 Git。

## 11. 更新与回滚

更新 `source/mysql8`：

```bash
bash package_all/build_plugin_repository.sh \
  --aggregation-home package_all/aggregation \
  --output-root /tmp/release/aggregation-plugins \
  --type source \
  --name mysql8 \
  --channel production \
  --release codex-20260804-source-mysql8-v2 \
  --runtime-version 1.0_jdk17-SNAPSHOT
```

然后按“先上传 release ZIP、最后更新 pointer”的顺序发布。Worker 后台刷新发现 v2 后，新任务实例使用 v2，已经运行的任务实例继续使用旧 identity。

回滚不重新生成或覆盖旧 ZIP，只需将 `current.json` 指向已验证的旧 release，并保持其 `sha256`、`size`、`runtimeVersion` 正确。回滚后新任务使用旧 release，正在运行的任务不发生版本漂移。

## 12. 常见错误

### `jq is required`

安装 `jq` 后重新执行：

```bash
sudo apt-get install -y jq
```

### `Aggregation plugin directory does not exist`

检查 `--aggregation-home` 是否指向包含 `plugin` 子目录的完整 aggregation 根目录：

```bash
test -d package_all/aggregation/plugin && echo OK
```

### `missing plugin.json` 或 `missing transformer.json`

普通插件需要 `plugin.json`；`transformer` 插件需要 `transformer.json`。配置文件中的 `name` 必须等于插件目录名。

### `does not contain a JAR`

插件目录必须至少有一个 `.jar` 文件。检查：

```bash
find package_all/aggregation/plugin/source/mysql8 -type f -iname '*.jar'
```

### `Existing immutable plugin release is incomplete`

目标 release 路径已经存在，但它不是包含 `plugin.zip` 的完整目录。不要覆盖或补写该目录；先确认它是否是未发布的本地残留，
并按发布流程处理后使用新的 release 重新构建。完整的既有 release 会打印 `SKIP`，不会触发此错误。

### `Plugin artifact size is outside the allowed range`

默认 ZIP 上限是 512 MiB。只有确认运行时限制已同步调整时，才通过 `--max-artifact-bytes` 提高限制；通常应减少插件依赖或拆分插件。

### pointer 摘要不匹配

不要手工修改 `sha256` 或 `size`。删除本地未发布的输出目录后，使用新 release 重新构建。

## 13. 发布前检查清单

- [ ] 使用的是完整 aggregation 插件目录，不是 Worker 的 cache/state 目录。
- [ ] `jq`、`zip`、`sha256sum` 已安装。
- [ ] 每个插件坐标唯一；既有 release 已核对完整性，确认可以跳过且不需要更新 pointer。
- [ ] 插件配置文件中的 `name` 与目录名一致。
- [ ] 每个插件都包含 JAR 和必需的配置文件。
- [ ] 本地 ZIP 的 SHA-256 和大小与 `current.json` 一致。
- [ ] 远程原 `current.json` 已备份。
- [ ] 先上传 release ZIP，再更新 `current.json`。
- [ ] 没有把 OSS/Nacos/数据库凭证写入命令、文档或提交。
- [ ] Worker 的 `runtimeVersion` 与 `current.json.runtimeVersion` 兼容。
- [ ] 更新或回滚只切换 pointer，不覆盖不可变 release。
